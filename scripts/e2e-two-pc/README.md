# Two-PC sync proof

This is the real-API/scratch-Postgres entry point for the two-device proof. It
uses the API's actual Hono routes and PostgreSQL persistence with synthetic
fixtures only. It does not read `DATABASE_URL`, VPS credentials, or any local
POS database.

## Safety gate

Provide a dedicated scratch database URL and repeat its exact database name in
`SMLPOS_E2E_ALLOW_SCRATCH_DB`. The runner accepts only a loopback PostgreSQL
host, rejects names that do not contain a
`test`, `scratch`, or `e2e` marker, rejects names marked `prod`, `production`,
or `live`, and never prints the URL. The API integration fixture creates a
random schema, migrates only that schema, inserts generated test users and
business rows, and drops the schema in `finally`.

From the repository root in PowerShell:

```powershell
$env:SMLPOS_E2E_TEST_DATABASE_URL = 'postgresql://user:password@localhost:5432/smlpos_e2e_test'
$env:SMLPOS_E2E_ALLOW_SCRATCH_DB = 'smlpos_e2e_test'
node scripts/e2e-two-pc/run.mjs
```

The runner defaults to `--seeds 20`; `--seeds N` selects a reproducible
sequence of seeds 1 through N, with 200 high-level operations per seed. It
prints the seed and a failure immediately if a run fails. Run `--seeds 50`
locally against a disposable PostgreSQL instance for the requested stress run.
The generator produces sales, returns, price changes, stock adjustments and
category deletions; writes accumulate in offline windows and device drain
order varies. The runner checks replica counts, sale totals in millimes,
stock for every product on both devices and the server, price, duplicate sale
numbers, pending outbox entries and pull rejects. Some pushes are replayed
after newer pushes. The replica SQLite connection is closed and reopened, and
HTTP requests are aborted after a seed batch and push are applied and in the
middle of a pull page. These are network aborts, not operating-system kills.

**External mode** accepts only `--base-url http://127.0.0.1:23001`, requires
the disposable API's staging-only flags, and reads a synthetic `desktop-proof`
admin credential as JSON from stdin. It runs one seed per disposable staging
project; whole-project teardown is its server cleanup. Its server stock check
reconstructs product stock from the server's immutable movement events; the
local mode additionally queries the PostgreSQL records directly. A pass does
not by itself represent physical two-PC validation.

The endpoint is intentionally opt-in: missing or mismatched scratch database
settings fail before any connection is made. Do not put production credentials
in these variables.

## What it proves today

The runner invokes `deploy/api/test/sync2.test.ts`, which seeds a synthetic
workspace, activates it, issues two independent device logins, exercises
idempotent sales upload and paginated pull, checks stock movement recomputation,
tests concurrent stock DELTAs from two devices, verifies integer-millime money
DELTAs, and confirms invalid DELTAs are rejected without blocking a later
valid operation. Every fixture row and credential is generated by the test.

The runner then starts the actual Hono API on loopback and launches an isolated
Electron-as-Node worker with two independent SQLite databases and the production
desktop adapter. It verifies seed/activation, an interrupted join followed by a
database and service restart, first-touch lock release only after verification,
lost push acknowledgement replay, offline sales and line items from both PCs,
stock movement deltas, customer balance deltas, and final row/count convergence.
Temporary user-data directories and the random Postgres schema are removed at
the end.
